# Responses API Empty-Output Recovery

## Task summary

Read Codex task `019f4a75-f52c-7830-a1da-37e8e60c4e99`, the two latest
handoffs, and the latest application logs. The previous task had completed the
Settings-wheel/cooldown isolation and translation-inactivity continuity
increments, then started investigating diagnostic log volume.

The new 14:01 runtime session showed the relay returning HTTP 200 to Responses
API translation calls, followed by `Responses API response did not contain
output text`. This was not caused by the application's `2/2` display, which is
only the local active-call count. The provider treated a structurally empty
HTTP 200 response as final and never attempted a bounded compatibility
recovery.

The provider now retries exactly once when a Responses API translation result
has no output text. In `auto` structured-output mode the retry removes JSON
Schema and accepts plain text; `strict` and `off` preserve their contracts.
The retry rechecks terminal status, includes both request durations, and stops
after the second empty result. Whitespace-only top-level `output_text` no
longer hides valid nested output or bypasses recovery.

Added a content-free recovery log containing only response status, structural
counts, and token counts. It excludes source/translated text, response bodies,
instructions, response IDs, URLs, metadata, and credentials. Malformed or
non-finite usage counts cannot interrupt recovery.

## Root-cause and live-probe evidence

- Latest app log at 14:01:
  - Responses requests returned HTTP 200 in 3.9-8.2 seconds;
  - parsing then failed because no output text was present;
  - the UI correctly displayed the resulting translation error.
- A raw `gpt-5.4` probe returned the standard completed Responses structure
  with nested `output_text`.
- Two simultaneous `gpt-5.4` probes both returned valid output and parsed, so
  local concurrency was not the cause.
- Model discovery returned 16 models, including `gpt-5.4`, `gpt-5.5`, and the
  real 5.6 names `gpt-5.6-luna`, `gpt-5.6-sol`, and `gpt-5.6-terra`. A prior
  probe of the nonexistent bare alias `gpt-5.6` must not be interpreted as the
  relay lacking GPT-5.6 support.
- Post-fix real provider probe:
  - `gpt-5.6-terra` completed successfully through the full provider path;
  - `gpt-5.4`, `gpt-5.5`, `gpt-5.6-luna`, and `gpt-5.6-sol` returned relay
    HTTP 502 Bad Gateway in that probe window. Existing transient HTTP recovery
    remains responsible for those provider-side failures.

No credentials or full response bodies were printed during probes.

## Important decisions

- Did not change local translation concurrency; `2/2` is an activity counter,
  not evidence of the relay's concurrency limit.
- Did not remove, hide, or mark GPT-5.6 unavailable. The relay exposes named
  GPT-5.6 variants and `gpt-5.6-terra` succeeded live.
- Did not add unbounded retries. One empty HTTP 200 can recover; a second empty
  result remains a visible error.
- Did not hide HTTP 502 errors or retry them at the display layer.
- Preserved the existing capability-aware schema rejection fallback.
- The design document was committed as `dd2f9af`; implementation remains
  uncommitted because the same files contain earlier mixed working-tree work.
