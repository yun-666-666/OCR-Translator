# Task summary

Rechecked the latest GUI logs after the user reported faster OCR plus several
Custom AI translation errors, then made another small OCR-side optimization.

Latest log findings:

- The latest run around 2026-07-06 16:42-16:44 shows OCR can be much faster
  when the subtitle fast path succeeds: many frames are around 0.031s-0.047s.
- Some frames still fall back to full PaddleOCR. In the last short session
  starting at 16:43:56, all 23 OCR samples fell back or behaved like fallback,
  averaging about 0.384s.
- The previous longer session starting at 16:42:44 had 415 OCR samples:
  325 fast-path recognitions averaged about 0.069s, while 90 fallback samples
  averaged about 0.248s.
- The log showed noisy recognized lines such as `7/#7$%8...`, and those lines
  were sometimes included in multi-line OCR results, slowing recognition and
  hurting translation quality.
- The Custom AI errors were not explicit HTTP 429/concurrency-limit errors.
  The logged error was:
  `Streaming API response did not contain message content`.
  Concurrent translations did cause queueing (`active calls 1/2` or `2/2`), but
  the visible error came from an empty streaming response from the provider path.

Root cause:

- `prepare_paddleocr_subtitle_line_images()` returned immediately when no
  bright pixels were found, so it skipped the edge/local-contrast fallback that
  was meant to rescue dim/low-contrast subtitle text.
- `flatten_paddleocr_text_recognition_result()` accepted high-confidence symbol
  noise as normal subtitle text, so non-dialogue crops like scoreboard/UI noise
  could be joined into the OCR result.

Implemented fix:

- If bright-pixel extraction has no usable pixels, the cropper now tries the
  edge/local-contrast mask before giving up.
- TextRecognition flattening now filters symbol-heavy subtitle noise lines
  before they enter the returned OCR text.
