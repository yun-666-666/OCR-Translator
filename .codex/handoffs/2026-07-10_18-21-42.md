# Handoff - PySide translation single-pass rendering

## Task summary

Completed the next bounded major optimization after re-reading the latest two
handoffs and the newest runtime log. The active PySide translation path rendered
every displayed translation twice: `DisplayManager` called `set_rtl_text()` and
then `configure(font=...)`, whose compatibility implementation rendered the
same stored text again.

The display manager now supplies the font family in the original render call.
`RTLTextDisplay` applies a changed font before building HTML, skips identical
font requests, and rerenders once only when a legacy `config(font=...)` caller
actually changes the font.

## Files changed or created

  - Removes the redundant follow-up `configure(font=...)` call.

## Important decisions

- Font application is part of the same atomic display operation so the first
  and only HTML render uses the requested family and size.
- The optional sixth parameter keeps all existing five-argument callers valid.
- `setFamily()` is called only for an explicit, real family change. This avoids
  destroying Qt's fallback-family chain when old callers change only size.
- Repeated `config(font=...)` requests are true no-ops: no `setFont()`, no HTML
  render, and no repeated font-update log.
- A read-only code review found the fallback-family issue; a red/green test and
  follow-up review closed it. The final review found no Critical or Important
  issues.

## Remaining issues or next steps

- No fresh manual GUI session was available after this code change. The real
  offscreen Qt component and backup/current A/B probe provide deterministic
  render-count evidence; a later normal user session can confirm perceived
  smoothness without being required for correctness.
- The next strong optimization candidate from the inspected log is content-safe
  translation logging: each translation text/result is repeated across several
  pipeline boundaries, accounting for about 20 KB in the inspected session.
- Adaptive capture backoff and higher translation concurrency were not selected:
  measured capture time was low, while concurrency would increase provider cost
  and risk without evidence of stale-response pressure.
- Earlier provider configuration remains unchanged in this increment: the relay
  profile still uses the persisted, live-tested `gpt-5.6-sol`, and the xAI
  profile remains unchanged.
