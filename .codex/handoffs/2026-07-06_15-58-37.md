# Task summary

Investigated the latest PaddleOCR live run and fixed the realtime behavior that
made it feel slow and unreliable.

Latest log evidence from `translator_debug.log` showed:

- The app was correctly using `ocr_model = paddleocr`.
- PaddleOCR no longer crashed.
- PaddleOCR recognized some subtitles, including `Will you eat me, Mr.
  Pussycat?`, `Goodbye. Goodbye.`, and `Here, kitty kitty!`.
- It ran too slowly for the existing realtime pipeline: 54 OCR samples averaged
  about 0.62s, with most warm frames around 0.4-0.9s and some restart/stop
  overlap samples around 3.2s.
- Only 3 OCR results reached translation during that run.

Root causes found:

- PaddleOCR was using the same FIFO OCR queue as Tesseract. With a 100ms
  capture interval and 0.4-0.9s OCR time, the queue could process stale frames
  instead of the latest subtitle.
- PaddleOCR non-empty results still had to pass the legacy
  `stability_threshold` repeat counter before reaching the newer local OCR
  stability gate. With `stability_threshold = 2`, short subtitles could vanish
  before they were submitted.
- The default PaddleOCR setting used `small` + `upscale 2.0`, but a local
  benchmark showed `tiny` + `upscale 1.0` recognizes a subtitle test image while
  running far faster after warmup.

# Important decisions

- Did not reduce the global `stability_threshold` setting. Instead, PaddleOCR
  bypasses the old repeat counter and uses the newer local OCR stability gate,
  so Tesseract behavior is not intentionally changed.
- Kept the scan interval at 100ms. The latest-frame queue prevents stale backlog,
  and the tiny model benchmark is close enough to this interval after warmup.
- Did not add visible PaddleOCR tuning controls in this pass.
