# Instant Cache Pending Invalidation Handoff

## Task summary

Completed a ninth large translation scheduler and cache-latency optimization.

An instant translation-cache hit previously displayed immediately but left an
older queued request and its scheduled callback alive. That callback could later
submit obsolete text, wasting a network request and competing with newer work.

The scheduler now has `_invalidate_pending_translation_request()`, which:

- advances `pending_translation_flush_generation`;
- clears `pending_translation_request`;
- clears `pending_translation_flush_scheduled`;
- resets `pending_translation_flush_deadline_monotonic`;
- logs invalidation only when pending/scheduled work existed.

The instant cache-hit path calls this helper before display. It also advances
`latest_translation_sequence_started` to the cache-hit sequence in addition to
the existing displayed sequence. Any callback carrying the old generation is
ignored, and older active final results remain unable to overwrite the cached
display.

## Important decisions

- Invalidated callbacks by generation instead of storing/canceling GUI timer
  IDs, matching the scheduler's existing stale-callback design.
- Made cache-hit sequence authoritative for both started and displayed ordering.
- Kept active HTTP calls untouched; their final responses are rejected by
  sequence ordering and may still populate useful caches.
- Initialized pending fields lazily for compatibility with lightweight app
  objects and tests.
- `.codex/release-artifacts/` remains untouched and excluded.

## Remaining issues or next steps

- Already-running obsolete provider calls cannot be safely canceled at the
  synchronous HTTP layer.
- Future work can use telemetry to identify other stale request sources or
  improve persistent cache observability.
