# Task summary

Implemented adaptive Custom AI latency mode. Users can now choose
`custom_ai_latency_mode = adaptive`; each translation request resolves that
strategy to a stable request-level `safe`, `stream`, or `race` mode before it is
submitted.

The advisor uses recent real Custom AI translation durations, consecutive
errors, provider cooldown state, stream capability, and healthy equivalent race
profiles. It defaults to `safe`, resolves high p90 latency to `stream`, resolves
very high p90 latency with multiple healthy equivalent profiles to `race`, avoids
race while its cooldown is active, and falls back to `safe` while the primary
endpoint is cooling without a healthy alternative.

Worker/handler integration now creates a latency request snapshot before
in-flight de-duplication, passes the resolved mode through cooldown checks and
the async worker, and uses the same resolved mode for provider calls. The
resolved mode remains part of the in-flight key; persistent translation cache
params continue to use the existing semantic request contract rather than adding
a mode-only cache split.

# Important decisions

- Kept adaptive as a policy layer. The Custom AI provider still receives only
  resolved transport modes for translation requests.
- OCR uses `safe` when the shared latency setting is `adaptive`; OCR does not
  currently participate in the translation latency advisor.
- Race is committed only when a translation request is actually submitted, so a
  queued request or cache hit does not consume the race frequency window.
- Adaptive race uses existing equivalent-profile filtering, cooldown filtering,
  credential-scoped identity, and busy-profile suppression.
- Stream partial display remains controlled by the existing worker sequence
  callback path; adaptive only decides whether that path is used for the request.
- No API keys or request secrets are added to adaptive logs.
