# Transient Translation Request Recovery Handoff

## Task summary

Completed a third large translation reliability and quality optimization.

Non-streaming Chat Completions and Responses requests now recover once on the
same known URL when the first attempt fails with:

- HTTP 502;
- HTTP 504;
- a recognized TLS EOF or connection-reset exception.

Owned pooled sessions are discarded and rebuilt before a TLS/reset retry.
Injected clients are retried without changing ownership. Both attempts remain
inside the existing duration measurement, output-limit capability fallback,
URL-memory, error sanitation, and endpoint fallback flow.

The retry is deliberately disabled for:

- latency mode `none`;
- streaming requests;
- permanent request/authentication errors;
- 429 and 503 responses;
- any response carrying `Retry-After`.

`Retry-After` on any error response now activates provider cooldown and stops
alternate path probing, rather than immediately sending another request.

## Important decisions

- Kept retries to one attempt and only narrowly recognized failures. This
  improves subtitle success rate without multiplying permanent failures.
- Did not retry generic read timeouts because the relay may already have
  processed and billed the request.
- Did not retry streaming failures because partial text may already be visible.
- Closed the first 502/504 response before retrying so pooled connections can be
  released promptly.
- Preserved a final alternate-path fallback after the same-URL retry is
  exhausted, except when cooldown or deterministic failure rules stop it.
- `.codex/release-artifacts/` remains untouched and excluded.

## Remaining issues or next steps

- Real-network recovery frequency depends on the selected relay.
- Future large optimization work can focus on quality-aware response validation
  or adaptive endpoint health scoring.
