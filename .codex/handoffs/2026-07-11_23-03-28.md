# Cost-protected Custom AI profile failover handoff

## Task summary

Diagnosed and fixed the high-cost subtitle failure path for Custom AI relay
profile `234`.  The latest log showed 33 calls in roughly 16 seconds: 15 HTTP
200 responses were forced SSE frames with no usable completion, then 18 HTTP
403 responses reported that prepaid credit could not be reserved.  Small OCR
text changes caused repeated submissions because the application had no
profile-level failure circuit.

The translation path now uses every enabled Custom AI profile sequentially:
selected profile first, then the remaining enabled profiles in saved order.  It
checks every eligible profile cache before making a network call, stops at the
first cache hit or successful translation, and does not change the user's saved
active profile.

## Behavior implemented

- A non-stream Chat Completions request that a relay incorrectly returns as a
  valid SSE stream is accepted when the stream contains text deltas.
- A forced SSE response with no translation, an HTTP/provider error, or an
  invalid returned translation marks only that profile unavailable for 60
  seconds in memory.  No keys or full provider payloads are kept in this state.
- `safe`, `none`, and `stream` modes check all enabled profile caches first,
  then call profiles sequentially once each.  Explicit `race` mode retains its
  existing parallel-cost contract.
- A successful profile clears only its own unavailable state and stores the
  translation under its current cache contract.  This preserves the existing
  automatic structured-output fallback cache behavior.
- The scheduler considers the same failover candidate list.  It runs
  immediately if any enabled profile is healthy; if all are cooling down, it
  waits for the earliest expiry instead of continuing one request every submit
  interval.
- If only one profile exists, the app keeps returning its existing redacted
  upstream error detail.  If multiple profiles are exhausted, it returns one
  concise all-profiles-unavailable message.

## Important decisions

- Automatic fallback is sequential, not parallel.  It minimizes billed
  duplicates while still using the user's other enabled configurations.
- No paid live API request was made after the fix because the failing relay had
  insufficient prepaid credit and the issue was fully reproducible from the
  captured log plus deterministic tests.
- Existing unrelated module-split and route-adaptive-timeout working-tree
  changes were preserved.  No commit, push, release, or profile-file edit was
  performed.

## Remaining notes

- A relay that returns SSE without text is still upstream-invalid; the app now
  handles it safely and fails over rather than treating it as a valid JSON
  translation.
- On the next ordinary subtitle session, `234` should be attempted once only;
  if it remains invalid or lacks prepaid credit, a healthy enabled fallback is
  used.  If none are healthy, the scheduler pauses until the earliest cooldown
  expires.
