# Task summary

Implemented Custom AI reasoning effort support for per-profile presets.
Profiles now default to `low`, normalize saved values to `low`, `medium`,
`high`, or `ultra`, and expose a localized "Reasoning effort" dropdown in the
AI model profile form.

Custom AI translation and OCR payloads now include reasoning effort by default.
Chat Completions requests send `reasoning_effort`; Responses API requests map
that to `reasoning: {"effort": "<value>"}`. Model-list and profile-test
requests do not add reasoning effort.

Added automatic reasoning-effort fallback. When a translation or OCR request
gets an explicit 400/422 unsupported reasoning/thinking/effort parameter
response, the provider retries once without the reasoning field. If the stripped
retry succeeds, it remembers the unsupported combination by request kind, wire
API, canonical endpoint, model, payload field format, and effort. Translation
and OCR memory are isolated, and one rejected effort does not disable the other
effort levels.

Updated translation in-flight/cache params and API OCR frame cache mode keys to
include the effective reasoning contract (`low`, `medium`, `high`, `ultra`, or
`none`). Existing output-limit safeguards remain active with reasoning enabled;
`max_tokens`/`max_output_tokens` fallback still removes output limits only when
an endpoint rejects them.

# Important decisions

- Kept reasoning effort per Custom AI profile, not global config, because the
  requirement says the setting belongs to each profile.
- Used `reasoning_effort` for Chat Completions and `reasoning.effort` for the
  Responses API, centralized in provider helpers so future wire-format changes
  stay local.
- Fallback triggers only for explicit 400/422 unsupported reasoning/effort
  parameter errors. Auth errors, rate limits, 5xx, and other non-capability
  failures do not strip or remember reasoning effort.
- Memory is request-kind scoped, so OCR fallback does not suppress translation
  reasoning and translation fallback does not suppress OCR reasoning.
- Cache and in-flight keys use the effective contract. Known unsupported
  combinations become `none`, preventing cache reuse across reasoning levels or
  stripped requests.
- Retained existing output-limit behavior with reasoning enabled; endpoints that
  reject output limits still use the existing output-limit fallback path.
