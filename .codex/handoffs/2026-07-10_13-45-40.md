# Task summary

Completed the second major optimization in the ongoing project audit: preserve subtitle continuity during short OCR gaps and prevent the translation worker from clearing the overlay while translation work is still active or pending.

The latest application log window showed 47 translation-overlay clears, and all 47 occurred while one or more translation calls were active. The old worker loop only considered local display inactivity and an empty OCR source string. It did not consider active calls, in-flight identities, pending requests, pending flush timers, the legacy queue, OCR-stability candidates, newer UI display activity, or whether the same display epoch had already been cleared.

The new behavior:

- blocks inactivity clears while source text, active work, pending work, queued work, or OCR-stability work exists;
- checks those blockers both when scheduling and again on the Tk UI thread;
- invalidates a scheduled clear if a newer success or error display appears;
- applies at most one clear for each display epoch;
- routes the real clear through the display manager's UI-thread updater;
- resets local OCR submission identity only after a real clear so the same subtitle can be translated again when it returns;
- records a content-free `translation_inactivity_clear` runtime metric and a single applied-clear log.

# Important decisions

- Did not merely increase `clear_translation_timeout`; that would hide, not fix, the race seen in the log.
- Used `(last_successful_translation_time, last_displayed_translation_sequence)` as a display epoch so both successful translations and visible error messages invalidate stale clears.
- Rechecked state on the Tk UI thread because work can appear after the worker schedules a clear.
- Kept the change inside the existing translation lifecycle and display manager rather than adding another timer/thread.
- Preserved unrelated pre-existing worktree changes; the design document was committed separately as `2f34891` (`docs: design translation inactivity continuity`), while implementation files remain part of the user's mixed working tree.
