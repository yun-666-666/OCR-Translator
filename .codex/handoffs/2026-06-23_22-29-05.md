## Important decisions made

- Kept all edits inside `C:\Users\wordy\Desktop\OCR-Translator-3.9.6-experiment`.
- Used two parallel subagents for speed, then explicitly closed both after use.
- Treated `2026-06-23 22:02:43-22:09:12` log traffic as test noise and `2026-06-23 21:18:09-21:38:48` as the relevant live window.
- Did not change UI, settings surface, or the user's config values.
- Kept the downstream queued-latest translation behavior intact so cooldown periods can still refresh to the newest OCR text.
- Increased `custom_ai` translation pacing for long OCR payloads by making submit interval scale with text length instead of always using a fixed `1.0s`.
- Added an upstream local-OCR gate so the Tesseract loop respects provider submit pacing before repeatedly calling `start_async_translation()`.
- Deliberately did **not** make the upstream OCR gate block on provider cooldown duration, because that would freeze pending-request refreshes and risk sending stale OCR text after cooldown expiry.
- Extended provider cooldown activation to also treat `503`/capacity-style responses with `Retry-After` as backoff triggers, based on a light web check of HTTP `Retry-After` behavior for `429` and `503`.

## Current status

The experiment copy is verified green. The current active `custom_ai` path is now more defensive in two places:

- Long OCR text is paced more conservatively before remote translation submission.
- Capacity-style provider responses (`429` and `503` with `Retry-After` / busy wording) now trigger cooldown, reducing repeat hammering when the endpoint is already overloaded.

## Known issues or follow-up work

- `last_successful_translation_time` is still used partly as a scheduling timestamp rather than a pure “successful display” timestamp. It works for current throttling, but the name is misleading and a future cleanup could split request-time vs success-time semantics.
- The new pacing is content-length-aware, but it is still heuristic. A later pass could make it adapt to observed RTT / retry-after history / provider profile.
- The app still lacks a strong persistent disk cache on the active `custom_ai` path; current high-value next optimizations are persistent cache, smarter OCR near-duplicate reuse, and more adaptive scheduling.
- I did not perform a paid live provider run after the code change, so the fix is verified by logs + regression tests rather than a fresh real endpoint call.
