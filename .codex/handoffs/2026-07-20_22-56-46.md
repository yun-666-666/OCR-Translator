# Pending translation flush uses delay-aware guarded UI scheduler

## Candidate selection

Reviewed remaining live-path Tk / `root.after` sites after `9cab2a1`.

Candidates considered:

1. Pending translation flush still used raw delayed `app.root.after(delay_ms, ...)` without shutdown / `winfo_exists` / TclError guards. **Selected** after extending `_schedule_ui_callback` with optional `delay_ms`.
2. OCR stability flush delayed `root.after`. Deferred to a later round once delay-aware helper is landed and pending flush is validated.
3. Instant-cache Tk var read inside `start_async_translation`. Deferred: entrypoints already UI-scheduled.
4. Translation-sequence counter TOCTOU. Deferred: medium risk, broader locking design.
5. Compatibility `run_api_ocr` live Tk fallbacks without snapshot. Deferred: production path always supplies snapshot.

Selection criteria met for item 1:

- High confidence static proof: delayed flush is a real worker/UI boundary schedule without guards.
- Low risk: extend existing helper with keyword-only `delay_ms` defaulting to 0; preserve generation/deadline rollback on failure; keep pending request payload.
- <=4 files: only `worker_translation.py` + tests + handoff.
- Deterministic tests without network.
- Stability benefit: avoids post-shutdown delayed flush scheduling and aligns with other guarded UI schedules.

## Task summary

`_schedule_ui_callback` now accepts optional `delay_ms` and passes it to `root.after`. `_queue_pending_translation_request` schedules `_flush_pending_translation_request` through that helper. Schedule failure clears flush flags for the current generation, logs, and returns without raising while leaving the pending request payload intact for a later reschedule path.
