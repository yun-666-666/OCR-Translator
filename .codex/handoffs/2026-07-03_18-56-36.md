# Race Loser Request Suppression Handoff

## Task summary

Completed a seventh large translation performance and relay-load optimization.

Race mode returns the first successful profile, but already-running loser HTTP
calls cannot be canceled by `ThreadPoolExecutor.shutdown(wait=False)`. Before
this change, the next subtitle could start another request against the same slow
loser while its previous request was still running.

The handler now tracks active race futures by non-secret profile identity:

- profile ID when available;
- otherwise normalized base URL, model, wire API, and reasoning effort.

Race candidate selection now excludes profiles with an older unfinished future
when at least one candidate is idle. Each submission:

- marks the profile busy;
- attaches a done callback that releases it;
- rolls back the mark if executor submission fails.

The winning identity is also explicitly released before return. A slow loser
therefore stays out of subsequent races until its real call finishes, then
automatically becomes eligible again.

## Important decisions

- Tracked futures instead of trying to cancel synchronous `requests` calls,
  which cannot be reliably interrupted after they start.
- Excluded busy profiles only when another idle candidate exists; an unexpected
  all-busy state falls back to the original list instead of producing an empty
  race.
- Used no API key in identity state.
- Kept single-candidate calls outside race tracking because normal outer
  scheduling already serializes them.
- Preserved semantic and cooldown filtering before busy filtering.
- `.codex/release-artifacts/` remains untouched and excluded.

## Remaining issues or next steps

- A slow loser still consumes its original request until completion, but it can
  no longer accumulate duplicate requests across following subtitles.
- Future optimization can add measured endpoint latency history to reduce how
  often consistently slow profiles are launched at all.
