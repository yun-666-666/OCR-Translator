# Output-limit capability and truncation recovery handoff

## Task summary

Completed two related translation quality and compatibility optimizations:

- added process-local output-limit capability memory keyed by wire API, normalized
  base URL, and model
- when a 400/422 response explicitly rejects `max_tokens` or
  `max_output_tokens`:
  - retry the same URL once without only that field
  - remember the capability
  - omit the field before later requests for the same provider identity
- applied the shared compatibility sender to:
  - Chat Completions
  - Responses
  - streaming Chat Completions
  - streaming Responses
- protected against false positives: numeric/range validation errors do not
  disable output-limit capability
- detected successful-but-truncated translations:
  - Chat `finish_reason=length`
  - Responses `status=incomplete` with reason `max_output_tokens`
- retried an explicitly truncated translation once without the application output
  limit, returning only the complete result to the translation handler and cache

## Important decisions

- Capability memory is process-local and does not rewrite profile configuration.
- Capability identity excludes API keys because field syntax support belongs to
  the endpoint/model protocol, not the secret.
- Compatibility retry uses the same URL once. Existing alternate-path fallback
  still handles endpoint-shape and gateway failures afterward.
- Detection requires both the exact field name and explicit unsupported/unknown/
  not-permitted wording.
- Numeric/range messages are excluded before unsupported wording is considered.
- A truncation response does not mark the field unsupported: the endpoint accepted
  the field, but the particular translation needed more output.
- Truncation recovery is limited to one retry and only runs when the original
  translation payload included the application output limit.
- Existing `.codex/release-artifacts/` content remains untouched.
