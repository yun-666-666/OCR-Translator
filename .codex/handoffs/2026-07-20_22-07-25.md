# Local OCR UI-thread translation routing

## Task summary

Implemented the remaining high-confidence live-path fix from the 2026-07-20 readonly re-review: Local OCR no longer enters `start_async_translation` (and therefore the translation/subtitle state machine / Tk instant-cache path) on the OCR worker thread.

Stable local OCR candidates still run recognition, stability gating, and near-duplicate skip logic on the worker. Only the final `start_async_translation(...)` call is scheduled through the existing `_schedule_ui_callback` helper. Schedule failure returns `"dropped"` and does not forge a `"submitted"` state.

## Important decisions

- Added a thin `worker_ocr._schedule_ui_callback` facade that calls `worker_threads._schedule_ui_callback`, matching the existing `_start_async_translation` facade pattern.
- `_submit_final_local_ocr_text` now schedules `start_async_translation` with positional args so `root.after(0, callback, *args)` can invoke it without keyword packing.
- On schedule failure, return `"dropped"` (already accepted by the OCR worker route-result checks) and log a coalesced message. Do not mark local OCR submit state, do not advance translation sequences, and do not call translation/display code.
- Existing stability/dedup tests that previously expected an immediate worker-thread `start_async_translation` call were updated to drain the scheduled UI callback deliberately.
- The PaddleOCR routing acceptance test was updated the same way so it still proves first clear text submits without the legacy stability threshold, while also requiring UI scheduling.
- Pre-existing uncommitted work was preserved:
  - `handlers/translation_requests.py` (429 / cooldown classification)
  - `tests/test_custom_ai.py`
  - `worker_threads.py` (API OCR cache-hit UI routing + earlier re-exports)
