# Shared translation error contract handoff

## Task summary

Completed an error-state correctness and retry-readiness optimization:

- traced translation result classification from `TranslationHandler` through
  `process_translation_response()`
- reproduced current Custom AI errors entering the worker success branch
- reproduced legitimate translations such as `Missing`, `Failed`, and
  `Not available` being rejected by the handler’s broad substring classifier
- added one strict, case-insensitive `is_translation_error_result()` contract in
  `translation_utils.py`
- covered current Custom AI, missing-profile, and legacy provider error prefixes
- changed `TranslationHandler._is_error_message()` to use the shared classifier
- changed the worker to use the same classifier instead of its stale local tuple
- stopped error responses from updating `last_successful_translation_time`
- preserved visible error display and sequence ordering
- cleared local OCR submission deduplication state after errors so the same source
  can be retried

## Important decisions

- Kept the public string-returning translation API for compatibility.
- Replaced broad substring matching with explicit prefixes; ordinary translated
  words no longer suppress caching or context.
- Kept error display visible and advanced the displayed sequence so an older
  successful response cannot overwrite a newer failure.
- Did not mark an error as a successful translation timestamp.
- Used a single shared contract to prevent handler/worker drift.
- Existing `.codex/release-artifacts/` content remains untouched.

## Remaining issues or next steps

- Errors now leave state retry-ready, but there is no new automatic retry scheduler
  in this pass.
- A future transient-only retry should distinguish cooldown/capacity/transport
  failures from permanent authentication or configuration errors.
- No paid or real-network request was made.
