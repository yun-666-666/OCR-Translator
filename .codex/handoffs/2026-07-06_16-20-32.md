# Task summary

Rechecked the latest application/debug log after the user reported PaddleOCR
was still too slow and still failed on subtitles.

Log evidence:

- The latest true GUI live run still appears to be the 2026-07-06 15:48 run.
- That run used `ocr_model = paddleocr`, but it was still using the full
  PaddleOCR detector/recognizer path.
- Live PaddleOCR timings in that run were too slow for subtitles: common warm
  frames were about 0.47s to 0.89s, with an initial 3.2s sample.
- The later 16:09-16:18 log lines are mostly direct backend benchmarks/tests,
  not a fresh GUI run. Those lines show the new subtitle fast path recognizing
  sample subtitle text and falling back to full OCR only for low-confidence
  noise-like crops.

Root cause:

- Full PP-OCRv6 detection over the entire subtitle capture area is too slow for
  realtime subtitle updates.
- Feeding the whole wide subtitle region to detection also makes subtitle text
  easier to miss because much of the image is background or non-subtitle visual
  content.

Implemented fix:

- Added a PaddleOCR subtitle fast path that crops bright subtitle text bands and
  sends those crops directly to PaddleOCR `TextRecognition`, skipping full text
  detection when possible.
- Kept full `PaddleOCR` as a fallback when no usable subtitle crop is found or
  the fast-path recognition confidence is too low.
- Updated realtime OCR routing so live PaddleOCR uses
  `recognize_subtitle_with_paddleocr()` instead of the full detector path.
- Kept PaddleOCR defaults optimized for subtitles: `tiny` model and
  `upscale = 1.0`.
- Added tests for subtitle crop extraction, fast-path routing, fallback behavior,
  and live worker routing through the subtitle fast path.
