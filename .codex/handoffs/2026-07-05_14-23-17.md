# Task summary

Implemented API key secure storage for Custom AI profiles and legacy provider
configuration keys.

Custom AI profile keys now migrate from plaintext `api_key` fields into a
credential reference backed by the system credential store. Runtime profiles
still resolve the in-memory key for provider calls, while JSON persistence uses
`api_key_ref` and strips plaintext when the credential write succeeds.

Traditional provider keys for Google Translate, DeepL, Gemini, and OpenAI now
migrate through the shared credential store during config load/save. The app
resolves refs back into Tk variables at startup so existing provider call paths
continue to read from the same variables.

# Important decisions

- Added `credential_store.py` with a small abstraction over Windows Credential
  Manager first, optional Python keyring fallback elsewhere, and an unavailable
  store for safe degradation.
- Used stable Custom AI refs shaped like `custom-ai:{profile_id}:api_key`.
- Used stable provider config refs shaped like
  `provider:{setting_key}:api_key`.
- Custom AI `get_profile()` and `get_active_profile()` remain runtime-facing and
  can include in-memory `api_key`; `serialize_for_disk()` is the explicit
  persisted form.
- If a credential write is unavailable, plaintext fallback is retained and a
  diagnostic log is emitted without the secret, so user keys are not silently
  lost.
- Profile deletion attempts credential deletion and logs sanitized failures
  without blocking deletion.
