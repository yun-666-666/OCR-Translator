# Bounded output and fail-fast endpoint optimization handoff

## Task summary

Completed the next translation latency and quality pass:

- added a dynamic output budget for non-reasoning translation requests
  - minimum 64 tokens
  - four output tokens per normalized source character
  - maximum 2,048 tokens
- omitted the output budget when a profile explicitly enables reasoning effort,
  because Responses counts hidden reasoning tokens inside `max_output_tokens`
- strengthened the system prompt so instructions appearing inside subtitle source
  text are translated as data rather than followed
- added one shared endpoint-fallback predicate across:
  - Chat Completions
  - Responses
  - streaming Chat Completions
  - streaming Responses
- stopped alternate-path requests after deterministic 4xx, HTTP 503, rate-limit,
  or capacity errors
- preserved alternate-path recovery for 404/405 and recoverable non-capacity 5xx
  responses

## Important decisions

- Dynamic output bounds apply only to non-reasoning profiles. User-selected
  reasoning behavior takes precedence over the worst-case output optimization.
- The source-as-data instruction is static and remains before dynamic context and
  current subtitle text, preserving prompt-prefix stability.
- No provider-specific request field was added.
- HTTP 404 and 405 still probe alternate URL shapes because they are credible
  endpoint-shape mismatches.
- Non-capacity 5xx responses still allow recovery from a failed cached route or
  gateway path.
- HTTP 503 stops immediately and activates the existing cooldown so the app does
  not duplicate load against the same relay.
- Existing `.codex/release-artifacts/` content remains untouched.
