# Important decisions

- Prewarm is conditional on `ocr_model == "paddleocr"` so AI OCR does not load
  PP-OCRV6 at application startup.
- Prewarm reuses the same PaddleOCR settings builder as the worker thread, so
  the warmed engines match runtime OCR settings.
- The structured-output fallback is intentionally narrow: only after a transient
  stream failure has already fallen back to non-stream and the auto structured
  response is invalid. Normal safe/strict structured errors still fail as before.
- OCR text cleanup was kept to conservative text-level fixes, not crop
  refactoring.
- Did not revert or clean existing dirty worktree changes from previous sessions.

# Remaining issues or next steps

- If the user clicks Start within the first few seconds after launch, prewarm may
  still be running. The log-verified prewarm run took 7.31s on this machine.
  A future guard could show "preparing local OCR" or make the OCR thread wait for
  an in-progress prewarm before consuming frames.
- Fast subtitles can still be missed when full PaddleOCR fallback hits long-tail
  durations or when the selected source area includes large non-subtitle text.
  The next step should add diagnostics for PaddleOCR queue drops, stability-gate
  pending/submit/drop counts, and translation pending overwrites.
- Consider a small bounded PaddleOCR frame buffer for rapid subtitles instead of
  keeping only the latest frame during long OCR calls.
