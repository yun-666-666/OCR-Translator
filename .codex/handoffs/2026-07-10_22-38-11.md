# Live Custom AI Profile Model Switch Optimization

## Task summary

Inspected the latest application logs and completed one bounded major
optimization for the reported Custom AI translation stalls.

The relay stall was an application state/UI issue layered on an upstream
failure. The `gpt-5.6-sol` Responses request returned HTTP 502 in 0.344 seconds
and entered a request-scoped 60-second cooldown. The user then selected 5.5 in
the fetched-model combobox, but that combobox only changed a Tk form variable;
the runtime profile remained `gpt-5.6-sol` until the separate Save button was
pressed. New subtitles therefore continued to observe the old model cooldown
and were queued for 58.5, 52.7, 37.5, and 32.0 seconds.

Explicit model-list selection and Enter now persist the selected model
immediately. If the edited profile is active for translation, the scheduler
invalidates the old cooldown timer and re-evaluates the newest subtitle on a
generation-checked callback. One old request can use the existing bounded
overflow slot, but total provider concurrency remains capped at two.

Provider request data is now immutable across a live profile edit. The profile,
language route, cache parameters, context generation, and latency decision are
copied at submission and passed through the thread pool to the HTTP call. An old
response remains associated with its old model/cache identity and cannot write
context into the new profile generation.

## Log findings

- Latest xAI `grok-4.3` successful requests were mostly 3.5-7.9 seconds, with
  one 20.172-second long tail and three 10-second read timeouts.
- Local queue and display scheduling were small; the HTTP request dominated.
- Short-log grouping on 2026-07-10 found 109 `grok-4.3` calls with P50 4.594s,
  P90 7.046s, average 4.977s, and maximum 20.172s.
- The same day's older `grok-4.20-0309-non-reasoning` data had 301 calls with
  P50 0.640s, P90 0.813s, average 0.681s, and maximum 2.375s.
- Both model groups ran in the version containing the xAI prompt-cache routing
  header. The available evidence therefore points to the model choice/upstream
  service as the dominant xAI latency change, not `x-grok-conv-id` or local
  scheduling. The cache header was not removed speculatively.

## Important decisions

- Kept the 10-second subtitle request timeout and maximum two active provider
  calls. Higher concurrency would increase cost and rate-limit risk without
  reducing the measured upstream service time.
- Preserved credential-wide HTTP 429 cooldown. Only model/wire-specific gateway
  failures can be escaped by selecting another model.
- Auto-apply is limited to an explicit combobox selection or Enter. Merely
  typing a partial model filter does not persist it.
- Did not silently change the user's xAI model or latency mode. Historical data
  proves the older non-reasoning model was much faster, but availability and
  quality are user/provider choices.

## Remaining issues or next steps

- No paid live API call was sent after this change. The next normal user session
  should confirm that selecting 5.5 causes an immediate request and the log no
  longer shows the 5.6 cooldown delaying it.
- `grok-4.3` itself remains materially slower than the previous non-reasoning
  model. Application scheduling cannot remove that upstream/model latency.
- The next major optimization should be selected from a post-change live log.
  A strong candidate is provider first-token instrumentation plus a measured
  safe/adaptive streaming policy, but prior xAI stream-empty failures mean this
  should not be enabled speculatively.
