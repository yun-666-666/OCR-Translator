# Handoff — Adaptive slow-route overflow protection (2026-07-23)

## Task summary

Added route-scoped adaptive protection that temporarily disables the bounded translation overflow slot when the current provider route is proven slow by real latency data. Healthy routes keep existing overflow behavior. The previous 250ms overflow candidate stability gate is unchanged.

Live motivation:
- Run A (healthy): discard 22.8%, worker avg 1.323s
- Run B (slow network): discard 73.3%, worker avg 2.640s, many overflow slots still opened and later discarded

## Design

### Data sources already present
- `request_snapshot["route_p90_seconds"]`
- `request_snapshot["route_sample_count"]`
- worker completion samples from `process_translation_async()`

### Enter protection (route-scoped)
Any of:
1. `route_sample_count >= 8` and `route_p90_seconds >= 3.0s`
2. two consecutive successful worker samples `>= 5.0s`

### Exit / recover
Any of:
1. `route_sample_count >= 8` and `0 < route_p90_seconds < 2.5s`
2. three consecutive successful worker samples `< 2.0s`

### While protected
- first free concurrency slot still submits immediately
- instant cache / in-flight dedupe / pending latest replacement unchanged
- bounded overflow second slot is blocked
- only the latest pending request is kept
- race mode still never uses overflow stacking
- configuration_refresh still bypasses slow-route protection
- stop/start clears protection state via `reset_translation_scheduler_session_state()`

### Metrics / logs
- counter `translation_overflow_protection_entered`
- counter `translation_overflow_protection_blocked`
- counter `translation_overflow_protection_recovered`
- coalesced logs:
  - `LATENCY: overflow protection entered ...`
  - `LATENCY: overflow blocked by slow-route protection ...`
  - `LATENCY: overflow protection recovered ...`

No OCR/translation body content is logged.

## Why Run A is unaffected
Healthy Run A worker avg ~1.3s is well below enter thresholds (`p90 >= 3.0s` or streak of `>=5s` workers). Overflow remains available after the existing 250ms candidate stability gate.

## Why Run B-like sessions improve
When route p90 climbs into the 3.5s+ range or workers repeatedly exceed 5s, opening a second overflow HTTP call is mostly waste: it completes after newer text has already started. Protection stops that second slot and keeps only pending latest until the route recovers.
