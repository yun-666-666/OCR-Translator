# Adaptive Translation Context Budget Handoff

## Task summary

Completed an eighth large translation speed and context-quality optimization.

Historical real-profile short logs contained 242 translation records. Profiles
with usage telemetry ranged from roughly 288 to 5435 average input tokens and
reached 5678 input tokens. The previous fixed 4000-character historical context
budget could significantly amplify already-long OCR requests.

Historical context now uses this request-specific formula:

```text
max(600, 2400 - min(1800, len(current_source)))
```

Behavior:

- no/empty current source: 2400 context characters;
- 40-character subtitle: 2360;
- 600-character source: 1800;
- 1200-character source: 1200;
- 1800+ character source: 600.

Selection still:

- honors the configured context entry count;
- excludes the current source;
- prioritizes the newest approved source/translation pairs;
- returns selected entries chronologically;
- truncates one oversized newest pair in balanced source/translation halves;
- includes the exact selected context in the cache identity.

The current source itself is never truncated. For long sources, maximum appended
history falls from 4000 to 600 characters, an 85% reduction in avoidable context
input. Short dialogue retains substantially more history for terminology and
voice consistency.

## Important decisions

- Used a deterministic local formula rather than model summarization, so no
  extra request, latency, cost, or failure mode is introduced.
- Preserved rich context for short subtitles instead of globally lowering the
  budget.
- Counted the raw source string exactly as documented; markup therefore consumes
  budget rather than creating a hidden alternate formula.
- Kept the existing recent-first selection and balanced pair truncation logic.
- `.codex/release-artifacts/` remains untouched and excluded.

## Remaining issues or next steps

- Character count is a provider-independent approximation rather than an exact
  tokenizer count.
- Real latency gains should be measured in future live sessions using the
  existing input-token and duration telemetry.
