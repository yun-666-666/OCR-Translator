# Context cache and streaming efficiency optimization handoff

## Task summary

Completed five coordinated Custom AI translation optimizations:

- fixed context-sensitive cache identity so an immediately repeated subtitle does
  not miss merely because the first result was added to its own history
- excluded the current source from its request context, avoiding self-reference
- refreshed repeated source entries with the newest accepted translation and
  allowed distinct sources to share the same translated text
- bounded request context content to 4,000 characters while preserving newest
  context first
- coalesced token-sized streaming UI callbacks and skipped a duplicate final
  widget update when the stream already displayed the same processed result
- preserved provider-reported cached input token counts for both Chat Completions
  and Responses usage shapes and recorded the numeric value in short logs

## Important decisions

- Cache keys remain context-sensitive; context was not removed globally because
  that could reuse a translation produced under materially different history.
- Only history entries matching the current source are excluded, so immediate
  repeats recover the intended cache hit without lowering contextual quality.
- Context budgeting is dependency-free and deterministic. It walks newest-first,
  preserves chronological order in the prompt, and truncates only when the newest
  entry alone exceeds the ceiling.
- Streaming still shows partial translations; it now keeps only the newest partial
  while one Tk callback is pending.
- No OpenAI-specific request parameter was added to Custom AI payloads because
  third-party compatible relays may reject unknown fields.
- Official OpenAI guidance was used only to validate static-prefix/dynamic-suffix
  prompt structure and cached-token monitoring. The local application cache and
  relay compatibility boundaries remain authoritative.
- Existing untracked `.codex/release-artifacts/` content was left untouched.
