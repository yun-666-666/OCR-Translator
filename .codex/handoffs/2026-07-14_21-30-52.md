# Overlay Startup Readiness and First-Click UX

## Task summary

- Implemented behavior B: the source and target overlays start hidden, while their last saved coordinates are restored and prepared for immediate use.
- Fixed direct Start after application launch so missing overlay objects are rebuilt from valid saved geometry instead of showing `Source area overlay missing. Select source area.`.
- Improved the first Hide/Show Source/Target Window interaction by preparing overlays before PaddleOCR prewarm, avoiding redundant target restyling, and flushing tkinter/PySide visibility events before settings I/O.
- Kept the work scoped to application startup and day-to-day overlay UX; OCR recognition and translation request behavior were not tuned.

## Real application verification

- Launched `main.py` with both visibility flags false and the saved coordinates:
  - source: `[288, 1000, 1653, 1185]`
  - target: `[298, 1185, 1502, 1380]`
- Runtime log confirmed both overlay objects were created hidden before PaddleOCR prewarm.
- Restarted and clicked Start without reselecting an area or toggling a window first.
- Start preflight passed, translation worker threads started, and no overlay-missing dialog appeared.
- Repeated target visibility toggles responded in approximately 58-93 ms.
- Stopped and closed the application cleanly; no application process remained running.

## Important decisions

- Both overlays are hidden at normal launch, regardless of the previous visibility flags, but retain their last geometry.
- Overlay readiness is idempotent and can recreate destroyed windows as well as initially missing windows.
- Start remains the final repair boundary so a delayed or failed startup callback cannot recreate the original error.
- PaddleOCR prewarm now begins after the overlay-readiness callback (250 ms versus 50 ms); its model loading/recognition implementation is unchanged.
- The pre-existing untracked `Dango-Translator-Ver6.3.1/` directory was not inspected, edited, staged, or committed.
