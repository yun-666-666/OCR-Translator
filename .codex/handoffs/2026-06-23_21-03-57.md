# Custom AI Responses parsing and model-list compatibility handoff

## Task summary

Fixed the experiment copy only. The user reported that adding/testing relay profile information still broke model-list fetching, and that both local-OCR-to-translation and GPT-5.5 translation showed `Custom AI translation error: ValueError - None`.

Root cause was confirmed against the live `api.e2ez.com` Responses endpoint: successful Responses API replies include `"error": null`. `custom_ai.py` treated the mere presence of an `error` key as a real error, so a successful response was converted into `ValueError("None")` before extracting `output[].content[].text`.

The model-list path also had narrow parsing and poor error-body handling. It expected only OpenAI-style `data: [...]`, so top-level `models: [...]` responses failed, and relay errors like `{"code":"INVALID_API_KEY","message":"Invalid API key"}` could be reported as a generic missing-data-list error.

## Important decisions made

- Kept the fix in the Custom AI provider parsing layer rather than changing the GUI.
- `error: null` is now ignored for Chat Completions, Responses, and model-list parsing.
- Real error payloads still raise, including nested `error.message` and top-level `code/message` relay errors.
- Model-list parsing now accepts `data`, `models`, nested `data/models`, and simple string entries while preserving the existing de-duplication behavior.
- For Responses profiles, existing fallback to the configured model is unchanged when model-list endpoints are unavailable and a model is already configured.
