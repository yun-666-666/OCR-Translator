# F1: translation pre-send obsolete gate

## Candidate selection

From the request-waste audit (`docs/cleanup/request-waste-api-quota-audit-2026-07-21.md`), only F1:

Translation worker (`process_translation_async`) could still call
`translate_text_with_timeout` after a newer sequence had already been submitted,
burning remote quota for results that response-side discard would drop.

OCR already skips pre-send via `batch_sequence_counter` in `process_api_ocr_async`.
Failover already skips obsolete candidates mid-chain. Worker entry for the first
HTTP attempt did not.

## Task summary

1. Added `worker_threads._translation_request_is_obsolete(app, sequence)`.
   - Prefers `translation_handler._custom_ai_translation_is_obsolete` so worker
     and failover share the same predicate.
   - Fallback mirrors that predicate exactly:
     - `request_sequence < latest_translation_sequence_started` (**strict `<`**)
     - or `request_sequence <= last_displayed_translation_sequence`
2. `process_translation_async` returns before building stream callbacks / calling
   `translate_text_with_timeout` when obsolete.
3. Early return still hits the existing `finally` cleanup:
   - `active_translation_calls`
   - `active_translation_inflight_keys`
   - `active_translation_started_monotonic`
   - `_expedite_pending_translation_request`
4. Response-side `stale_response_discarded` path unchanged for already-started HTTP.

Why strict `<` on latest_started: `_submit_async_translation_request` sets
`latest_translation_sequence_started = translation_sequence` for the request that
is about to run. Using `<=` would treat the current request as obsolete and kill
the only live translation.
